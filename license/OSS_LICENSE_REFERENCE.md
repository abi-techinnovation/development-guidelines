# OSSライセンスリファレンス

このリファレンスはOSSや関連するライセンスの主な特徴を確認するための資料である。実際の判断では対象物に含まれるライセンス本文と追加条項を優先する。

## 1. 用語

| 用語 | 意味 |
| --- | --- |
| OSS | OSIのOpen Source Definitionに適合するライセンスで提供されるソフトウェア |
| プロプライエタリ | 利用、改変、再配布などを権利者が独自条件で制限するソフトウェア |
| ソースアベイラブル | ソースは閲覧できるが、用途、競合、商用利用などの制限によりOSSとは限らないもの |
| 利用許諾 | 権利者が条件の範囲内で著作物の利用を認めること |
| 配布・提供 | 複製物を組織外へ渡すこと。販売、無償配布、納品、機器への搭載、コンテナイメージの提供などを含む |
| コピーレフト | 配布などの際、対象となる改変物や派生物にも同じライセンスやソース提供を求める仕組み |
| SBOM | Software Bill of Materials。ソフトウェアを構成する部品と依存関係の記録 |
| SPDX ID | `MIT`、`Apache-2.0`、`GPL-3.0-only`などの標準化されたライセンス識別子 |

## 2. 主なライセンスの分類

| 分類 | 代表例 | 主な義務・特徴 | 原則的な判断 |
| --- | --- | --- | --- |
| Permissive | `MIT`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC` | 著作権表示とライセンス文の保持が中心 | 通常利用可。配布物の第三者告知へ収録する |
| Permissive・特許許諾あり | `Apache-2.0` | LICENSE、変更表示、該当するNOTICEを保持する。明示的な特許許諾がある | 通常利用可。NOTICEと変更記録を確認する |
| ファイル単位のWeak copyleft | `MPL-2.0` | 未改変も含め、対象コードを実行形式で配布する場合は対象ソースをMPLで入手可能にし、取得方法を通知する | 対象ファイルを分離・追跡できる場合に利用する |
| ライブラリ単位のWeak copyleft | `LGPL-2.1-only`、`LGPL-3.0-only` | LGPL部分と改変のソース提供、差し替えや再リンクを可能にする条件などがある | リンク方法と配布形態を確認する |
| Strong copyleft | `GPL-2.0-only`、`GPL-2.0-or-later`、`GPL-3.0-only` | 配布時に、結合物を含む対応ソースの提供とGPLでの許諾が必要になる場合がある | 独自製品への組込み、リンク、派生物は要確認とする |
| Network copyleft | `AGPL-3.0-only` | 改変版をネットワーク越しに利用させる場合も、対応ソースの取得機会を提供する | SaaS、Web、API、社外利用は法務確認する |
| 条件のない許諾型 | `0BSD` | 著作権表示の保持を許諾条件としない。権利放棄とは異なる | 出所と版を記録し、特許・商標は別に確認する |
| Public domain相当・権利放棄型 | `Unlicense` | 権利放棄と許諾の条項を持つ。法域ごとの有効性は別に確認する | 出所と版を記録し、重要部品は特許条項も確認する |
| 非OSS・独自条件 | SSPL、各種BSL、Elastic License、Commons Clauseなど | 用途、競合サービス、商用利用、提供形態などを個別に制限する | OSSとして扱わず、採用前に契約を確認する |

MPLの配布条件は[本文3.1〜3.3節](https://www.mozilla.org/en-US/MPL/2.0/)を参照する。0BSDは[OSI掲載の本文](https://opensource.org/license/0bsd)に表示保持の条件がなく、権利放棄型とは分けて扱う。

## 3. よくある義務

### 3.1 著作権表示とライセンス文

バイナリだけを配布する場合も免除とは限らない。アプリ内のライセンス画面、同梱ファイル、製品マニュアルなど、受領者が確認できる場所へ掲載する。

### 3.2 NOTICE

Apache-2.0の依存物にNOTICEがある場合は、ライセンス本文に従い、該当する帰属表示を読みやすい形で引き継ぐ。無関係な情報を機械的に混ぜない。

### 3.3 対応ソース

実際に配布したオブジェクトコードを生成するためのソースやビルド用スクリプトなどを含む場合がある。上流URL、差分、別バージョンのソースだけでは不十分になる場合がある。

GPLv3の対応ソースは生成・インストール・実行・改変に必要なソースと制御用スクリプトを含み、システムライブラリなどには例外がある。提供方法は配布形態に合わせて[GPLv3第6節](https://www.gnu.org/licenses/gpl-3.0.en.html#section6)から選ぶ。物理製品に添える書面による申出は、少なくとも3年かつ当該製品モデルの交換部品または顧客サポートを提供する期間にわたり有効である必要がある。この期間をすべてのGPL配布へ一律に当てはめない。

GPLv3のUser Productに該当する機器などでは、改変版をインストール・実行するためのInstallation Informationが必要になる場合がある。機器の署名や起動制限も確認する。GPLv2など別の版はその本文で条件を確認する。

### 3.4 同一ライセンス

コピーレフト対象を、受領者にも同じ自由を与える条件で提供する。独自のNDAや再配布禁止を対象コードへ上乗せできない場合がある。

### 3.5 特許と商標

著作権の利用許諾と特許許諾は同じではない。すべてのOSSライセンスがApache-2.0と同等の特許許諾を含むわけではない。また、OSSライセンスは通常、プロジェクト名やロゴの商標利用まで許諾しない。

LGPLv3の結合著作物では、ライブラリ部分の改変とそのデバッグのためのリバースエンジニアリングを契約で制限しない条件がある。再リンク用の対応アプリケーションコード等を提供する方法と、改変済みライブラリでも動作する適切な共有ライブラリ方式などを[第4節](https://www.gnu.org/licenses/lgpl-3.0.en.html)に沿って確認する。動的リンクという名称だけでは判断しない。

AGPLv3第13節はプログラムを改変した者に対し、その改変版がネットワーク越しの対話に対応する場合、対話するすべての利用者に、その改変版の対応ソースを無償で取得する機会を目立つ形で提示するよう求める。社内向けという理由だけで除外しない。複製物を渡す場合の条件も別に確認する。[AGPLv3本文](https://www.gnu.org/licenses/agpl-3.0.en.html#section13)を参照する。

## 4. 利用形態ごとの注意点

| 利用形態 | 確認事項 |
| --- | --- |
| 開発ツールとして実行 | 成果物へのコード混入、テンプレートや生成コード、プラグインの条件 |
| 社内サーバー・社内端末 | AGPL、外部常駐者、別法人、契約条項 |
| SaaS・Web・API | AGPL、SSPL、独自のSaaS制限。通常のGPLはネットワーク利用だけで配布義務が生じるとは限らない |
| 顧客へのバイナリ納品 | LICENSE、著作権表示、NOTICE、対応ソース、再許諾条件 |
| コンテナ・VM・機器への搭載 | OSパッケージ、ベースイメージ、CLI、フォントなど、アプリ以外の同梱物 |
| モバイル・デスクトップ配布 | アプリストア規約、DRM、署名、再リンク可能性 |
| ソースコードのコピー・改変 | スニペットの著作物性、元ファイルのヘッダー、変更表示、履歴 |
| 別プロセス・API・IPC連携 | 通信方式、密結合性、同時配布、設計上の独立性 |
| 顧客指定OSS・受託開発 | 自社の遵守責任、成果物の権利保証、補償条項 |

単一法人内で複製して使用するだけなら、通常はGPL系の配布条件が発動しにくい。一方、別法人への移転、顧客環境へのデプロイ、端末貸与、成果物の引渡しは個別判断が必要になる。

## 5. ソフトウェア以外のライセンス

| 対象 | 注意点 |
| --- | --- |
| ドキュメント・画像・動画 | Creative Commonsなどを確認する。`BY`は表示、`SA`は同一条件、`NC`は非商用、`ND`は改変物の共有を制限する条件を表す。版と利用行為を確認する |
| データ・データベース | 著作権だけでなく、データベース権、個人情報、利用規約、取得元との契約、営業秘密を確認する |
| フォント | `OFL-1.1`などの埋込み、改変、単体再配布、予約名称の条件を確認する |
| AIモデル・重み | コード、モデルの重み、学習データ、出力の条件を個別に確認する |
| API・クラウドサービス | SDKのライセンスとは別に、API利用規約、データ利用、再販売、地域、終了条件を確認する |
| 規格・サンプルコード | 規格文書の著作権、実装特許、サンプル固有のライセンスを確認する |

CCの`NC`・`ND`は[公式FAQ](https://creativecommons.org/faq/)と対象の版の本文で確認する。NDを私的な改変まで一律に禁止する条件と解釈しない。CCはソフトウェアへのCCライセンスの使用を推奨していない。

AIシステムの「オープン」と、重みがダウンロード可能であることは同じではない。[OSI Open Source AI Definition 1.0](https://opensource.org/ai/open-source-ai-definition)は、変更に適した形としてデータに関する情報、学習・実行用コード、パラメーターを区別する。定義への適合と、個々のコード・重み・データの利用許諾は別に確認する。

## 6. よくある誤解

| 誤解 | 正しい考え方 |
| --- | --- |
| GitHubに公開されているから自由に使える | ライセンスがなければ、原則として複製、改変、再配布の許諾はない |
| OSSは商用利用できない | OSI準拠のOSSは商用利用を排除しないが、配布時の条件などは守る |
| 無料のパッケージはOSSである | 無料配布とOSSは別であり、利用規約や独自ライセンスを確認する |
| 著作権表示を入れれば何でも使える | 表示以外に、ソース提供や同一ライセンスなどが必要な場合がある |
| 改変しなければ義務はない | 未改変でも、配布時に表示やソース提供が必要な場合がある |
| 動的リンクならGPLやLGPLの問題はない | リンク方式だけでなく、版、結合状態、再リンク可能性、配布形態を確認する |
| SaaSならソース公開は不要である | AGPLや独自ライセンスはネットワーク利用にも条件を課す場合がある |
| 社内で使えば安全である | 契約、AGPL、別法人、外部委託などの論点は残る |
| SBOMを作れば遵守できる | SBOMは在庫情報であり、条件の解釈、表示、ソース提供、承認は別に実施する |

## 8. SPDXライセンス式

[SPDX仕様3.0.1のライセンス式](https://spdx.github.io/spdx-spec/v3.0.1/annexes/spdx-license-expressions/)に従い、複数条件の関係を記録する。

| 式の例 | 意味と確認事項 |
| --- | --- |
| `MIT OR Apache-2.0` | いずれかを選べる。採用した条件を判断記録に残す |
| `MIT AND BSD-3-Clause` | 両方の条件を満たす。任意選択に読み替えない |
| `GPL-2.0-or-later WITH Bison-exception-2.2` | 指定ライセンスに指定の例外が付く。例外の対象と本文を確認する |
| `LicenseRef-Internal-Custom` | 利用者定義の参照。識別子だけで済ませず、対応する本文を保管する |

混在する式は括弧で適用範囲を明示する。例外を自社判断で追加したり、複数ファイルの異なる条件を一つの`OR`にまとめたりしない。SPDX式の記録だけでは、結合物の互換性や利用可否の審査は完了しない。
